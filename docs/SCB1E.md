# Broadlink SCB1E

The dedicated `SCB1E` driver uses the existing Broadlink pairing, UDP, AES and authentication layer. It supports these raw discovery types:

| Raw type | Protocol |
| --- | --- |
| `0xA56B` | SP4 |
| `0x5115` | SP4B |
| `0x6113` | SP4B |

The device's MAC identity and decimal `data.devtype` follow the existing pairing format. SCB1E is a separate compatibility family; it does not use the SP2 or SP3S state/control implementation.

| State field | Standard Homey capability | Homey unit |
| --- | --- | --- |
| `pwr` | `onoff` | boolean |
| `power` | `measure_power` | W |
| `totalconsum` | `meter_power` | kWh |
| `volt` | `measure_voltage` | V |
| `current` | `measure_current` | A |

SP4 values are passed through without added scaling. SP4B state reads divide `current`, `volt`, `power`, `totalconsum` and `overload` by 1000, omitting missing fields and fields equal to `-1`, exactly as upstream. `overload` is decoded for diagnostics only. Set-state responses retain upstream's raw values; only their relay acknowledgement is used before a separate full-state refresh. No additional scaling, energy estimation, reset command or undocumented setting is introduced.

One state request updates all available capabilities. Missing measurements and temporary protocol/network failures preserve the last valid values. Polling begins immediately and repeats one minute after completion by default; the existing Interval setting changes this delay in minutes. Concurrent poll requests are coalesced. A per-device queue serializes polling, relay commands and settings/authentication operations because `Communicate` has one pending UDP response callback. Failed operations do not poison the queue. Deletion stops timers and drains the bounded in-flight request before destroying communication.

New devices authenticate during their first poll. Existing stored credentials are reused on app restart. The existing Re-authenticate device setting can establish a new session if needed. The new driver handles the raw decimal device type consistently during authentication. Shared authentication diagnostics no longer print session keys or authentication response bodies.

`Communicate.send_packet()` adds `decryptedPayload` on successful responses. Existing `cmd` (first four decrypted bytes), `payload` (remaining decrypted bytes), error handling and return semantics are preserved. No existing driver, capability or Flow ID changes; no migration or dependency change is required. Standard Homey capabilities provide the standard relay actions/conditions and measurement-change Flows.

## Protocol reference and deterministic tests

Reference inspected on 2026-09-07: `mjg59/python-broadlink` commit `730853e5faf2cf979596662faf9def2b1f8fee6d`:

- [Device type mappings](https://github.com/mjg59/python-broadlink/blob/730853e5faf2cf979596662faf9def2b1f8fee6d/broadlink/__init__.py)
- [SP4/SP4B implementation](https://github.com/mjg59/python-broadlink/blob/730853e5faf2cf979596662faf9def2b1f8fee6d/broadlink/switch.py)

SP4 uses a 12-byte `<HHHBBI` header. SP4B adds a 2-byte length prefix (`12 + JSON byte length`). Both use compact JSON, flag 1 for reads and flag 2 for writes, byte `0x0B`, and a checksum seeded with `0xBEAF`; SP4B excludes the length prefix from this checksum. JSON response lengths are read at offsets 8 and 10 respectively, with JSON beginning at offsets 12 and 14. AES padding is excluded using the declared JSON length. Response checks follow upstream's error, length and JSON decoding behavior with additional state type validation; no speculative response flag/checksum requirements are imposed.

`tests/fixtures/scb1e.json` contains synthetic protocol fixtures generated by executing the pinned upstream `sp4._encode` and `sp4b._encode` methods in Python. The response fixtures use representative state values and upstream framing; they are not physical-device captures. Tests compare exact request bytes and cover both decoders, all five SP4B scaling fields, unsupported values, malformed messages, encrypted shared responses, legacy response slices, discovery mappings and driver lifecycle behavior. Python is not needed to run the committed tests.

Run local verification:

```sh
npm test
homey app validate
homey app validate --level publish
git diff --check
```

There is no configured application build or lint command. `homey app validate` regenerates `app.json` and the pairing view from Compose sources. Do not edit these generated definitions manually.

## Manual Homey/device smoke test (not yet performed)

1. Install the local app only when authorized. Pair SCB1E using its IP address. Confirm the discovery name and raw type, successful authentication, and the expected SP4/SP4B variant in logs. Repeat for each available hardware variant.
2. Confirm relay state and all supported measurements appear. Compare power, cumulative consumption, voltage and current against the device's own readings, including a zero-load state. For SP4B, compare raw protocol fields with the documented `/1000` normalization. Missing sensors should remain unknown rather than become zero.
3. Turn the relay on/off from Homey's device tile and standard Flow actions; check the actual load. Change the relay using the physical button/Broadlink app and confirm the next poll reflects it. Check the standard measurement-change Flows and Insights.
4. Temporarily make SCB1E unreachable. Confirm last readings remain, relay actions report errors and repeated polls do not overlap. Restore connectivity and confirm subsequent polling recovers. Use Re-authenticate device if the device has lost its session.
5. Restart the app with SCB1E already paired. Confirm credentials, identity, capabilities and Flows remain intact, with one polling schedule. Change the Interval and IP settings and exercise Re-authenticate device; verify the new values are used and the authentication checkbox clears.
6. Remove a test SCB1E during a pending read; verify no later capability writes or recurring polls. Check representative existing SP1/SP2/SP3S/RM/MP1 devices for startup, discovery/pairing, control, telemetry and existing Flows as applicable.

Static tests and package validation do not establish real Homey/device behavior. No physical-device communication, installation or publication is part of local verification.
